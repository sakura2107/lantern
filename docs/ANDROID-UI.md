# Android 界面（2026-10 重写）

本次只重写表现层。协议、权限、TLS、任务 journal、编解码、SAF 和线程所有权都没有改动；业务调用仍走 `Remote`、`FileBrowser`、`TransferQueue`、`AvcDesktop`、`SystemAudio`、`DesktopTools`、`Discovery` 和 `Secrets`。

## 设计语言

- **底色与墨色**：冷灰底（`#EEF1F4`）、白色卡片、蓝黑墨色（`#1B2430`）。主要操作用墨色实心按钮，次要操作用浅灰底按钮。
- **一盏灯**：琥珀色 `#F3A223` 只表示"正在工作"：已连接、画面正在接收、控制已开启、声音正在播放、传输进行中。设备页顶部的 `Lamp` 是整套界面唯一的表现性元素：未连接时熄灭，连接中呼吸闪烁，已连接时点亮，失败时显示红圈。
- **形状**：卡片用 1dp 细线、不加阴影；按钮是胶囊形。圆角按层级区分：页面卡片 22–24dp，列表行 16dp，输入框 14dp。
- **深色模式**：跟随系统，颜色 token 见 `Theme.java`。
- **图标**：`Glyph.java` 在 24 单位网格上绘制约 60 个线性图标，不依赖资源文件。
- **应用图标**：墨色圆角方块里的白色金属提灯和琥珀火焰，母版是 `assets/lantern-icon.svg`。
  - **自适应图标**：`res/mipmap-anydpi-v26/ic_launcher{,_round}.xml`。背景是 `drawable/ic_launcher_background.xml`（墨色渐变），前景是 `drawable/ic_launcher_foreground.xml`（提灯和光晕，按 72/108 缩进安全区）。两者都是由 SVG 手工转写的矢量图。
  - **为什么要自适应图标**：ColorOS 会把只有 PNG 的旧式图标缩小后放在白底上。
  - **PNG 备用**：`res/mipmap-{m,h,xh,xxh,xxxh}dpi/ic_launcher{,_round}.png` 只作备用。
  - **构建**：两个构建脚本都会用 aapt2 编译 `res/` 并链接。
- **构建方式**：
  - **完整构建**：`android/build-standalone.ps1`，需要 NDK。
  - **免 NDK 的 debug 构建**：`android/build-repack.ps1 -Tools <android-tools> -BaseApk <旧 debug APK> -Keystore <debug.keystore> [-Install]`。
    - 编译 Java，用 aapt2 链接清单、`resources.arsc` 和 `res/`。
    - `android/tools/Repack.java` 保留旧 APK 的原生库和 assets，换入新的 classes.dex 与资源。
    - 最后 `zipalign -P 16` 并签名。
    - Java 工具打不开含中文的源码路径，所以所有文件先复制到 `%TEMP%\lantern-repack` 再处理。
- **文案**：集中在 `S.java`，统一使用句子式中文。错误提示写明原因和下一步。协议层、传输层的消息原样显示，仍保留在各自的类里。

## 行为说明

- **三种"不显示"分开表述**：
  - "画面"开关：订阅或停止，停止后电脑不再采集；
  - "隐藏本机画面"：电脑继续发送，只是手机不显示；
  - "主机隐私屏"：明确标为不支持。
- **发现电脑不建立信任**：选中发现结果只会填入地址。随后的面板把对方声明的指纹按 4 位一组展示，只有用户点"一致，使用此指纹"才会填入；如果与已保存的指纹不同，会用红色警示。
- **指纹输入**：去掉空格、冒号、连字符并转成小写后，如果正好是 64 位十六进制就采用规范形式，否则原样提交，交给原有校验。
- **传输**：
  - 新增 `TransferQueue.remove`：只能移除"完成"或"已取消"的任务，并清理该任务的私有缓存；
  - 新增 `moveToTop` 和 `openDone`，是从原来的弹窗代码中抽出来的；
  - `clearCompleted` 复用同一个缓存清理函数；
  - 用户设定的限速保存在 `device` 偏好中。
- **复制/移动到根目录**：目标路径填 `/` 表示根目录。原来的实现会拼出 `"/name"`，而且空输入不会执行，所以这个场景以前无法完成。
- **其他小改动**：
  - 画面循环出错时会把开关状态同步回界面，原来按钮文字不变，现在开关能正确熄灭；
  - 未连接时点"开启画面"会直接提示，不再进入失败循环。

## 自动化标识

控件通过 `Ui.id(view, "…")` 设置稳定标识（view tag key `0x7f4c0001`），用 `Ui.find(root, id)` 查找，不依赖显示文字。`DeviceTestRunner.click()` 把原来的步骤名映射到这些标识，并用 `isActivated()` 检查开关的预期状态（例如"控制：开"要求控制开关已激活）。主要标识：

`device.connect`、`device.host`、`device.fingerprint`、`device.secret`、`device.discover`、`nav.device|desktop|files|transfers`、`desktop.subscribe`、`desktop.control`、`desktop.audio`、`desktop.hide`、`desktop.fullscreen`、`full.rotate`、`full.collapse`、`full.tools`、`full.exit`、`files.upload`、`files.search`、`files.sort`、`files.select`、`files.cancel`、`transfers.limit`、`transfers.pauseall`、`transfers.clear`。

## 扫码配对

后端接口和安全约束见 [PAIRING-BACKEND-HANDOFF.md](PAIRING-BACKEND-HANDOFF.md)。

- **三个入口，同一个确认流程**：
  - 设备页的“扫码配对”：打开 `ScanActivity`，首次使用时申请相机权限。
  - 配对信息里的“粘贴链接”。
  - 外部打开的 `lantern://pair?...` 链接，例如相机或聊天里的链接。`MainActivity` 改为 `singleTask`，链接会交给已有的窗口处理；处理后清除 intent 数据，重建窗口时不会重复配对。
- **按钮显示**：
  - 尚无可用配对时，主按钮是“扫码配对”（标识 `device.scan`），“连接电脑”降为次要按钮。
  - 已保存或已连接时，只在配对信息里保留“扫码配对”和“粘贴链接”（`device.form.scan`、`device.form.paste`）。
- **确认面板**：链接先用 `PairingLink.parse` 离线校验，失败时提示“二维码无效或已过期”。校验通过后弹出确认面板，显示电脑名称、第一个地址和指纹前 4 组，用户点“配对并连接”后才联网。
- **配对**：在后台线程调用 `Remote.pair(link, 设备名)`。设备名取“厂商 型号”，超过 64 字节时改用“Android 手机”。
  - **成功**：把地址、指纹和密钥填入表单，再走原来的 `pairDevice()`，因此保存、在线检测和自动连接都与手动配对相同。
  - **失败**：8 种失败原因（`PairFailure`）各有说明，见 `S.PAIR_ERRORS`，同时设备页进入“失败”状态。
- **`ScanActivity`**：
  - **相机**：Camera2 + TextureView，后置摄像头，竖屏；预览按中心裁剪，不会变形。
  - **解码**：从 YUV 帧中取亮度平面，交给 ZXing `QRCodeReader`（TRY_HARDER，只识别 QR 码），只解码中心 85% 的正方形区域。帧只在内存中处理，不保存。
  - **结果**：只接受以 `lantern://pair?` 开头的内容；其他二维码会提示“这不是 Lantern 的配对二维码”。识别成功时振动反馈，并把链接返回给调用方。
  - **界面**：取景框外压暗，四角琥珀色，中间有一条来回扫描的线；底部是“取消”和“粘贴链接”。
- **ZXing core 3.5.3**：Apache-2.0 许可，位于 `android/libs/`。两个构建脚本都会把它加入 javac 的 classpath 和 d8 的输入，许可文本随 APK 放在 `assets/licenses/`。
- **构建脚本修复**：`build-repack.ps1` 现在用 aapt2 `-A` 打包源码中的 `assets/`，`Repack` 把条目名里的 `\` 统一成 `/`。之前 Windows 上的 aapt2 会写出 `assets/licenses\…`，Android 找不到这些文件。

## 公网连接

后端接口见 [PUBLIC-NETWORK-HANDOFF.md](PUBLIC-NETWORK-HANDOFF.md)。

- **入口列表按电脑保存**：放在 SharedPreferences `device` 的 `endpoints_v1`，同时记下所属指纹 `endpoints_pin`。指纹换了就不再使用，也就不会把一台电脑的地址用到另一台上。令牌和指纹仍走原来的 Keystore 与偏好项。
- **配对**：`Remote.pair` 返回的入口先保存，再走原来的 `pairDevice()`。
- **连接**：`pairDevice()` 用输入框里的地址加上保存的入口一起竞速连接。
  - **连上后**：记下失败的入口（`ConnectionEndpoint.recordResults`），向电脑查询当前入口（`Remote.endpoints()`，旧主机返回空），合并后保存。之后的连接都用新的凭据对象。
  - **全部失败时**：设备页逐个列出每个地址的原因，失败次数也会保存。指纹不一致时直接停止。
- **在线检测**：每次（重新）连上，都更新当前使用的入口。
  - **网络切换**：Wi-Fi 和移动数据之间切换后，设备页会显示“局域网 · …”或“公网 IPv6 · […]”；转到公网时提示可以把画质调低一档。
  - **地址更新**：同时向电脑查询一次入口；有变化就保存，电脑换了 IPv6 前缀后，手机下次出门也能连上。
- **网络诊断**：原来的往返测量下面多了“各个地址”。每个入口单独并行检查（TCP、固定指纹的 TLS、不带权限的 HELLO，再 ping 一次），显示可用与往返时间，或者失败原因（超时、被拒绝、域名解析失败等）。
- **配对确认面板**：v2 链接显示第一个入口和入口总数。
- **真机验证（PKR110 / Android 16，2026-10-16）**：
  - **环境**：生成的测试主机开启公网访问，监听 `::`；手机用移动数据，通过 USB 共享网络连到电脑。
  - **局域网**：扫码链接为 v1、只含局域网 IPv4。配对后手机经 USB 共享地址连上，设备页显示“局域网 · 10.120.115.43:…”，并从电脑学到两个稳定的公网 IPv6 地址。
  - **公网（第一次）**：网络诊断里，这两个公网 IPv6 经移动数据都返回“被拒绝”。路由器上没有发现 UPnP，所以“让路由器自动放行”没有生效，也没有写入任何配置。当时电脑开着代理的 TUN 模式，手机也在给电脑做 USB 共享网络，回程路径不对。
  - **公网（用户自测，2026-10-16 晚）**：关掉 TUN 和 USB 共享后，手机只用移动数据。两个公网 IPv6 都显示“可用”，往返 37–53 ms，中位 63.9 ms；局域网地址按预期超时。当时家里宽带正处在晚间高峰，文件传输上限自适应降到约 0.3 MiB/s。
  - **诊断副标题**：之前显示的是保存的局域网地址，现在改为实际使用的路径（例如“经 公网 IPv6 · […]”）。
  - **数据恢复**：测试前后在手机上备份并恢复了原有的配对资料。

## 传输速度显示（2026-10-17）

  - **更正（2026-11-13，用户实测发现）**：之前这里写的“选 120 帧时实际显示 114–121 帧”是错的。那个数是解码器“交给屏幕”的帧数，不是屏幕真正显示的帧数。改为直接读系统合成器的上屏时间后：
    - ColorOS 的自适应刷新率在几秒不碰屏幕后，会把应用降到 60Hz（120Hz 屏幕上视频只显示约 57 帧），一触摸又回到 120Hz；
    - 窗口申请 120Hz 模式、帧率类别、内容速度提示、视频层“总是切换”、声明为游戏，这些都无效；
    - 有效的办法：画面解码期间，用 `VsyncClock` 每个刷新周期注册一次帧回调，应用就一直保持 120Hz 节拍；
    - 这一步之后，不碰屏幕时 120 帧档显示 78–95 帧，60 帧档 55–58 帧；

  - **再更正（2026-11-13，用户实测“720p 只有 85 帧、2K 反而 100+”）**：剩下的差额不是网络造成的，而是电脑端发帧节奏的问题。
    - 手机同时记录到达间隔和电脑采集时间戳的间隔，两者扎堆的比例一样（720p 约 20%），说明扎堆在电脑端就已经发生；
    - 电脑端逐帧计时：发帧循环用普通睡眠，Windows 按系统时钟粒度唤醒，中位数多睡 3.7 ms，最多 16 ms。睡过头后循环为了追帧会连发两帧；
    - 720p 编码快，两帧几乎贴在一起，落进同一次 8.3 ms 刷新，屏幕只能显示一帧。2K 编码本身较慢，补发的帧自然被拉开，所以反而显示得更多；
    - 修复：电脑端改用高精度可等待计时器（约 0.5 ms 精度），两次采集至少间隔 3/4 帧，迟到的帧不再紧跟着补发；
    - 修复后不碰屏幕：720p120 显示 110–115 帧，1080p120 102–112，2K120 103–111，1080p60 60 帧；边滑边看 720p120 105–109。电脑采集间隔的抖动从约 5 ms 降到 0.5 ms；
    - Wi-Fi 低延迟锁：修复后做了开/关对照，对帧到达的均匀程度没有可测的差别，所以没有采用；
